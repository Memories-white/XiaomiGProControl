# 键盘灯效：HID 输出链路分析

目标：`libXiaomiGCommandCenter.dll` 2.1.1.418（SHA-256 `0C18F391…F6397`）。
下文保留分阶段研究记录。早期“未实现写入”“仅开放波浪”的说明是当时状态；
当前 0.12.0 的实现和真机边界见文末“0.12.0 效果扩展与验证”。

## 结论先说

灯效**不经过 MiDeviceService**。它由客户端进程直接写 HID：

```
前端 cefQuery
  → LightEffectMessageHandler        ([HID] SET EFFECTPARAM AT BROWSER THERAD)
  → LightEffectManager::SetEffectParameter / SetPresetEffect
  → B21PayloadWriter::SetEffectParams(CommonSetting)
  → B21PayloadWriter::KeyBoard1ByteCmd(device, request, out response, len, opType, cmd)
  → HID WriteFile / read-back
```

`B21PayloadWriter` 的完整方法集（取自 `.rdata` 里的 RTTI/日志签名）：

| 方法 | 作用 |
| --- | --- |
| `GetHardwareVersion(unsigned char&, unsigned char&)` | 读硬件版本 |
| `GetEffectParams(Scene)` → string | 读当前效果参数 |
| `SetEffectParams(CommonSetting)` | **写效果参数（真正的输出口）** |
| `ExitEditMode()` | 退出编辑态 |
| `KeyBoard1ByteCmd(string, string&, ulong, OperatorType, uchar)` | 单条 HID 命令收发，唯一实际写设备的函数 |

反编译入口（脚本见 `scripts/`）：

| 函数 | 地址 | 说明 |
| --- | --- | --- |
| `SetPresetEffect` | `0x18017d4f0` | 解析参数 JSON、组装 `CommonSetting` |
| `SetEffectParameter` | `0x18017cf20` | 单参数设置 |
| `SetLedAreasValid` | `0x18017d0e0` | LED 区域有效位图 |

`SetPresetEffect` 内部没有直接的 HID/IO 调用，参数被写入效果结构后由灯效工作线程
（日志 `LightEffect Thread`）通过 `B21PayloadWriter` 下发，所以“改一个滑块”与“发出哪些帧”
不是一一对应的。

## 线上帧格式

固定 **65 字节**报文，头部 `00 57 AB <CMD>`：

```
00 57 AB 02 01 01 00 01 02 01 00 00 B3 00 … （补零到 65 字节）
```

`KEYBOARD1BYTECMD` 的响应体同样以 `00 57 AB` 开头，日志里以
`[HID] KeyBoard1ByteCmd return data: <hex>` 记录，可用于读回校验。

## 已观察到的命令

| CMD | 次数（单次会话） | 已确认的语义 |
| ---: | ---: | --- |
| 0 | 12350 | 心跳 / 状态查询 |
| 1 | 34 | 编辑/读写切换（配合 CMD 2 使用） |
| 2 | 11 | **设置块**：LED 区域位图 + 当前灯效状态 |
| 5 | 5 | 每次「应用/保存」后一次（疑似落盘/提交） |
| 12 (0x0C) | 12 | 每次应用前后成对出现（1 → 0），疑似编辑态开关 |
| 13 (0x0D) | 1 | 打开灯效页时一次 |

### CMD 2 的位图字节

载荷第 12 字节与日志中的 `SetLedAreasValid <mask>` 精确对应：

| `SetLedAreasValid` | 第 12 字节 |
| ---: | ---: |
| 11 (0x0B) | `B3` |
| 10 (0x0A) | `B0` |
| 9 (0x09) | `93` |
| 3 (0x03) | `A3` |
| 1 (0x01) | `83` |

规律：`byte = (mask << 4) | nibble`，低位 nibble 在 mask 为偶数时为 0、奇数时为 3，
语义尚未确认（可能是区域告警位或保留位）。

### CMD 2 其余字节随状态变化

同一会话内对比（键盘灯关闭 → 开启）：

```
关闭: 00 57 AB 02 | 01 FF 00 00 02 00 00 00 | 90
开启: 00 57 AB 02 | 01 01 00 01 02 01 00 00 | B3
```

差异出现在第 5、7、9、12 字节，说明**效果状态确实由 CMD 2 承载**（早先“参数不走这些帧”
的结论是错的，那是把不同状态的两帧误当成同一状态）。字段含义仍需逐项对照才能确定。

## 当时还没解决的部分（已由第二轮抓帧更新）

1. 各字段的具体语义（亮度 / 速度 / 方向 / 颜色类型 / 分区颜色）尚未逐个确认。
2. 颜色表（每个区域的 RGB）没有在 65 字节报文里出现，可能走编辑态下的多条 CMD 2，
   或以其它 `OperatorType` 发送。
3. 当时误把 CMD 12 视为编辑态；后续反编译确认它属于上盖/徽标状态刷新。

## 下一步需要的证据

操作步骤与回传格式见 [lighting-capture-guide.md](lighting-capture-guide.md)，抓帧工具为 `scripts/capture-light-frames.ps1`。


对同一场景做**单变量**改动，每次只改一项，并记录对应帧：

1. 只改亮度（2 → 1）
2. 只改速度（1 → 3）
3. 只改方向（2 → 4）
4. 只改颜色（青蓝 → 红）
5. 关闭再打开键盘灯效（已知会改变第 5/7/9 字节）

这五组对照足以把 CMD 2 的位域逐一定位，然后再决定是否值得为它实现 HID 写入
（需要独占一个 65 字节报文设备句柄，且写入错误可能让背光停在非预期状态）。

## 第一轮抓帧结果（2026-10-31 22:58–22:59）

### 关键发现：状态块在 CMD 1 的**回复**里

第一轮日志里同一秒出现的相邻序列如下；后续静态分析确认 CMD 12 属于上盖/徽标刷新，
不能把这段相邻日志当作键盘写入所需时序：

```
CMD 5  → reply       落盘/提交
CMD 1  → reply       读状态，回复里带当前效果块
CMD 2  → reply       写状态块（发送帧里带同样的块）
CMD 1  → reply       回读校验
CMD 12:1 → reply     上盖/徽标相关刷新
CMD 1  → reply
CMD 12:0 → reply     上盖/徽标相关刷新
CMD 1  → reply
```

CMD 1 回复帧布局（`00 57 AB 01` 之后）：

| 偏移 | 取值 | 含义（推断） |
| ---: | --- | --- |
| 4 | `01` | 固定 |
| 5 | `01` | 固定 |
| 6 | `00` | 固定 |
| 7 | `01` | 固定 |
| 8 | `00`–`03` | **唯一随设置变化的字段**，最可能是亮度/强度 |
| 9 | `01` | 固定（可能是速度=1） |
| 10–11 | `00 00` | 固定 |
| 12 | `A3` / `B3` | LED 区域位图（与 `SetLedAreasValid` 对应） |

CMD 2 的发送帧把同一块原样搬过去，只把第 3 字节换成 `02`——即
「读状态（CMD 1 回复）→ 写状态（CMD 2）」是同一个结构。

### 本轮观察到的取值

| 时间 | 帧 | 字节 8 | 字节 12 |
| --- | --- | ---: | --- |
| 22:58:46,080 | CMD 2 发送 | `00` | `A3` |
| 22:59:20,735 | CMD 2 发送 | `02` | `B3` |
| 22:59:21,865 | CMD 2 发送 | `03` | `B3` |

同一次应用里 CMD 2 被写了两次（旧值 → 新值），说明流程是先回写当前状态再写新值。

### 本轮数据不足的地方

五次抓帧全部标成了「第1步 亮度 2->1」，无法把取值变化对应到具体设置，
所以只能说"字节 8 就是被改的那个字段"，仍定不出它是亮度还是强度，
也定不出速度 / 方向 / 颜色分别在哪一位。

### 下一轮需要

每次只改一项，并且**用不同标签**运行脚本：

```powershell
.\capture-light-frames.ps1 -Label "亮度 2->1"
.\capture-light-frames.ps1 -Label "速度 1->3"
.\capture-light-frames.ps1 -Label "方向 2->4"
.\capture-light-frames.ps1 -Label "颜色 青蓝->红"
.\capture-light-frames.ps1 -Label "关灯->开灯"
```

只要 CMD 1 回复里除字节 8 之外的字节也动了，就能立刻定位那个字段。

## 第二轮单变量抓帧结果（2026-11-05）

五组使用了不同标签，原始输出保存在 `analysis-runtime/lighting-capture-*.txt`。
波浪模式下，CMD 1 回复字节 4–12 的实机对照如下：

| 单变量操作 | 变化 | 结论 |
| --- | --- | --- |
| 亮度 2 → 1 | `[8] 03 → 00` | 字节 8 是亮度编码；已知 3=2 档、0=1 档 |
| 速度 1 → 3（重试） | `[9] 01 → 03` | 字节 9 是速度编码；取值与界面档位一致 |
| 方向 2 → 4 | `[7] 01 → 00` | 字节 7 是方向编码；已知 1=方向2、0=方向4 |
| 波浪配色第 1 → 第 3 项 | `[6] 00 → 02` | 字节 6 是零基配色索引；选择时实时更新，应用阶段不再变化 |
| 键盘灯开 → 关 → 开 | 见下 | 关闭态与恢复态已验证可逆 |

开关往返的完整状态块：

```
开启: 01 01 02 00 03 03 00 00 B3
关闭: 01 FF 00 00 03 00 00 00 B0
恢复: 01 01 02 00 03 03 00 00 B3
```

因此当前已确认的布局是：字节 5 为效果/关闭标志（波浪=1、关闭=FF），
字节 6 为配色索引，字节 7 为方向编码，字节 8 为亮度编码，字节 9 为速度编码；
字节 12 高半字节是 LED 区域掩码，低半字节 3 表示开启、0 表示关闭。

初版先加入了读取原厂 `XGCC_log.txt` 的被动解析器；随后已升级为主动 HID 读取，
日志解析器仅作为失败回退。下节记录主动探针与写入验证结果。

## HID 传输与只读主动探针（2026-11-05）

对 `B21PayloadWriter` 的函数入口和下层包装器继续反编译后确认：

- RGB 键盘筛选条件：VID `0x1A86`、PID `0xE302`、接口标识 `mi_02`；
- 白光键盘使用 PID `0xE303`，本机当前目标不是它；
- `OpenKbdDevice` 最终以读写权限、共享读写调用 `CreateFileW`；
- `KeyBoard1ByteCmd` 通过 `WriteFile` 发送固定 65 字节报告，需要回复时用
  `ReadFile` 循环读取，直到回复第 3 字节 CMD 与请求一致；
- `GetHardwareVersion` 发送 CMD 6，从回复偏移 5、6 读取版本字节；
- 本机唯一 HID 接口为 `VID_1A86&PID_E302&MI_02`，实机 CMD 6 返回硬件版本
  `01.13`；CMD 1 主动读取返回值与原厂日志完全一致；
- 原厂控制中心同时运行时再次主动读取也成功，证明共享句柄路径可共存。

应用现优先使用 CMD 6/CMD 1 主动读取：先校验硬件版本，再读取当前状态；失败时才
回退到原厂日志。

## 受控写入与回滚验证（2026-11-05）

继续反编译 `SetEffectParams`、`SaveEffectParams`、`EnterEditMode` 和底层 HID 包装器后确认：

- `SetEffectParams` 使用 CMD 2，`SaveEffectParams` 使用 CMD 5；
- `EnterEditMode` 只是每秒发送 CMD 0 的心跳，CMD 12 不是键盘编辑态；
- 安全写入按 `CMD 1 备份 → CMD 2 写入 → CMD 1 校验 → CMD 5 保存 → CMD 1 校验`；
- 失败时用原始状态执行 CMD 2/CMD 5 并两次读回，回滚不受调用方取消令牌影响。

真机先完成速度 `3 → 1 → 3` 往返；随后完成整组往返：配色 `2 → 0 → 2`、方向
`0 → 1 → 0`、亮度 `3 → 0 → 3`、速度 `3 → 1 → 3`，最终 `restored=True`。
第一次整组恢复时亮度短暂保持在 0，稍后重写即恢复，因此正式回滚逻辑最多重试三次，
每次均执行写入、读回、保存、再读回。

`LightingPage` 只在硬件版本 01.13 且当前为已开启波浪效果时开放已抓帧值：配色编码
0/2、方向 0/1、亮度 0/3、速度 1/3。其他编码和其他效果继续禁用，直到分别得到真机证据。

## 键盘灯开关与配置保存（2026-11-06）

复用第二轮开/关抓帧：关闭将偏移 5 改为 FF，6/7/9 清零，保留亮度，偏移 12
由 B3 改为 B0；开启用之前已验证的波浪配置恢复，并设为 B3。仅接受硬件 01.13、
区域 B 和波浪/已关闭状态，使用现有 CMD 2 写入、CMD 1 校验、CMD 5 保存和回滚逻辑。

`GProControl.LightingProbe --validate-power-roundtrip` 真机结果：

```
power-off=verified

```

灯效页成功应用后保存配置，关灯前保留开启配置以便再次开启。启动按保存的开关和

## 0.12.0 效果扩展与验证（2026-11-06）

本轮在原厂 `dist/static/js/main.js` 中核对菜单、效果枚举和适用参数，并在现有
Ghidra 工程反编译 `CommonSetting` 打包函数 `0x1801922a0`，结合
`B21PayloadWriter::SetEffectParams`（`0x180124670`）确认本机 B21 帧布局。
这里的静态分析来自现有 Ghidra 工程，不冒充 REA 工具返回的 Evidence。

### 已验证的硬件模式与字段

| 效果编码 | 模式 |
| ---: | --- |
| 1 | 波浪 |
| 2 | 呼吸 |
| 3 | 涟漪 |
| 5 | 触发 |
| 6 | 彩色波浪 |
| 7 | 彩虹旋转 |
| 8 | 贪吃蛇 |
| 10 | 萤火虫 |
| 11 | 常亮 |
| 11，配色 FF | 自选 RGB 柔光（界面模式 23） |

以上模式完成 CMD 2 写入、CMD 1 读回、CMD 5 保存及保存后读回，随后恢复测试前的
原始配置。柔光的 RGB 字节在帧偏移 18–20，范围为 0–127；界面颜色转换为 7 位通道。
区域保持 B，灯光开/关仍使用低半字节 3/0。

新增参数验证包括配色 0/1/2、亮度 0/1/2/3、速度 1/2/3。彩色波浪方向 2 和长度
1/2 已通过；长度 3 被拒绝，界面只开放两档长度。速度 0 会被固件规范为 1，不作为
独立速度档位开放。不适用的参数由固件规范化，例如呼吸速度读回 2，触发、萤火虫和
常亮速度读回 0；校验只要求当前效果实际支持的参数匹配，不把规范化误判为应用失败。
这些结果是已执行的单项/模式验证，不代表所有参数笛卡尔组合均经过测试。

雨滴效果编码 4 和自定义像素配色 8 在本机验证中未被接受，程序已排除这两条路径，
没有通过忽略读回差异来假装支持。它们不作为本机原厂键盘菜单中的可用效果开放。

### 屏幕与声音联动

模式 22“光影随行”在用户启用后采样主屏幕 4×4 网格的平均颜色，模式 21“光音视界”
读取系统播放端点音量峰值并调节选定颜色亮度。两者均使用整键盘统一 RGB，**不等同于
原厂逐键屏幕图像映射或完整音频频谱呈现**。屏幕画面和音频内容不会保存或上传。

两种模式均完成启动、持续运行、停止和恢复原灯效验证：

```text
ambient=21; running=True; stopped=True
ambient=22; running=True; stopped=True
ambient-restored=True
```

动态效果仅在软件运行时生效，页面切换或转入后台不会停止。动画帧不执行 CMD 5，
避免持续写入键盘闪存；停止或正常退出时恢复之前备份的硬件灯效。

### 配置与复现

`LastLightingProfile` 保存常规效果，兼容旧 `LastWaveLighting` 配置。启动恢复仅应用
支持的常规配置和开关状态；屏幕/声音联动不在开机时自动启用。完整重启恢复验收仍待补齐。

```powershell
dotnet run --project tests/GProControl.LightingProbe -c Release -- --validate-all-effects
dotnet run --project tests/GProControl.LightingProbe -c Release -- --validate-ambient
```

这两个命令会短暂改变灯效并恢复。原始本机结果保留在
`analysis-runtime/all-effects-validation.txt` 和 `analysis-runtime/ambient-validation.txt`，不提交完整运行日志。
